Fallout.jl

Test impact analysis (regression test selection) for Julia packages: after an edit, run only the testsets the edit can affect. The selector never loads the package under test, so it runs from any environment (julia >= 1.12).

For long tests, units cache the expensive parts of a testset and reuse them while the code they ran is unchanged:

const CACHE = unit_cache()   # under --code-coverage=@. or Pkg.test(coverage = true)
replicates = [unit(simulate_replicate, CACHE, (; seed)) for seed in 1:200]

See units.md for how to write tests that use them.

It expects a test entry file (default test/runtests.jl) that holds top-level @testsets with literal names, and a runner script (default test/runtests.jl) that runs the testsets whose name matches a regex given as its first argument, as ReTest does.

Alternatively, with --suites DIR, every file under DIR whose name matches --suite-pattern (default ^test_.*\.jl$) is one testset, named by its path from DIR (systems/test_loop.jl). The runner then gets the selected paths as its arguments, one each, and a change to the runner selects every suite. A suite owns the files it includes: a code change in one selects the suite, and a testset in one is part of the suite.

Usage

Install it into an environment of its own, so it never touches the package under test:

julia --project=tia -e 'using Pkg; Pkg.add(url = "https://github.com/ParadaCarleton/Fallout.jl")'

Then run a command from the root of the package whose tests you want to select:

julia --startup-file=no --project=tia -e 'using Fallout; main(ARGS)' COMMAND [options]

From a clone, julia --startup-file=no bin/fallout.jl COMMAND [options] does the same. A typical session maps the suite once from a committed tree, then selects for each change:

fallout build --source src --jobs 8        # writes test-impact-map.toml
fallout select                             # testsets the change since the map can affect
fallout run                                # select, then run them

(fallout standing for either command line above.)

Build the map

Every top-level testset runs in its own process under --code-coverage=@<source dir>. The map records the tree's commit, every source file's function list, and which functions each testset executed. A runner that starts distributed workers would start them without the coverage flags: use --env to keep each testset in the coverage-flagged process (for ReTest-style runners, a variable the runner reads).

A build can be split into shards, dealt round-robin by source length and run from one tree so they share a commit, then joined:

for k in 1 2 3 4; do
  fallout.jl build --source src --jobs 8 --shard $k/4 --map shard-$k-map.toml
done
fallout.jl merge --map map.toml --in shard-1-map.toml --in shard-2-map.toml ...
  • In each shard the smallest testset runs alone first, so the coverage-flagged precompile is built once. The rest then run --jobs at a time, longest first.
  • merge refuses shards from different commits or files, and a testset mapped twice.
  • A testset's status is ok, failed, timeout or no-coverage. Only ok coverage is trusted in full; select selects every other status after a Julia source edit.

Static maps

Use fallout build --static to infer testset reach without running each testset. Fallout compiles top-level testset bodies as functions, follows optimized IR calls, and writes the same map format used by select. The build runs in the package project in a child process. The current tree must match --commit in Julia, environment, and test files.

fallout build --static [--unresolved approximate|follow-known|drop] [--cache DIR|none]
    [--workers N] [--setup-file FILE] [--test-module NAME]
    [--extra-testset-macro NAME[=PREFIX]]... [--progress-interval SECONDS]

approximate is the default. It follows known callees and maps every source function for a testset with an unknown callee. follow-known drops unknown callees; drop drops all dynamic sites. The build prints completed testsets and elapsed time every ten seconds by default, including work done in child processes.

The default loader reads test definitions without executing @testset bodies. Use --setup-file test/static_setup.jl --test-module PackageTests when a suite has its own loader. Use --extra-testset-macro 'custom_testset=custom: ' to name an additional macro's testsets with a prefix matching the runner. The cache defaults to .scratch/static-map-cache under the root and holds serialized Salsa query storage. Its key includes Julia, the Manifest, Fallout's walker, and source definition identities. Salsa re-infers frames whose source changes and retains a testset reach result when the frame's reached methods and callees stay the same.

select and run build an absent map statically. They refresh an older static map or walker before selection, using its recorded options. A map at HEAD remains the baseline for selecting uncommitted edits. Coverage maps continue to use their recorded commit.

Select

select diffs the map's commit against the working tree (untracked files included) or --to REV. The map's coverage describes the code at its commit, so a diff from any other commit can miss a testset: a call added on the trunk after the map was built is invisible to a diff from the branch's merge-base. --base REV replaces the map's commit; use it only when REV holds the same code. In a jj workspace that is not colocated, pass --to <commit of @>. Each selected testset is printed with the rule that chose it, followed by a regex for the runner.

ChangeSelected
Project.toml / Manifest*.toml (root or a source dir)the full suite

a function's signature, or a method added or removedtestsets that executed any method of that name
a struct, abstract/primitive type, const, global, macro, @enum, rule macro…testsets that executed a function mentioning one of its names, or whose own code mentions it. Names spread through definitions that mention them (const V = Vector{S}).
a using or importas above, for each name it no longer imports. A name it starts importing selects nothing by itself: code that starts using it is a change of its own.
a testsetthat testset
a test helper or test constanttestsets that mention it, transitively
a non-.jl file under the tests directorytestsets whose code or helpers name the file
any .jl filestatic-analysis testsets: JET, Aqua, readdir/walkdir/pkgdir scans and names(mod; all = true) introspection, and testsets using their helpers. A test name counts as such a helper only if every definition of it reads or analyses code or uses such a helper, and it is not one of Base's names: a struct whose constructor method reports through a scanning helper does not make every testset that builds the struct a static-analysis testset.
  • Blank lines, comments and docstrings are ignored. A change counts if the code tokens change, or if the items around it parse differently: a blank that changes the code ([1 -x] against [1 - x], return\nx against return x) counts.
  • An operator method (Base.:(==)(a::S, b::S)) is known by its operator, ==.
  • A changed function that no testset executed is printed as UNCOVERED. So is a new function that no testset runs or names.
  • A file that does not parse stops the selector with the parser's message.
  • The map lacks the functions added, renamed or re-signed since it was built; select prints how many of the changed functions that is (map lacks 2 of 9 changed functions) and lists them. Those are selected by name only (see "What a map knows"). As the map ages, the diff from its commit grows and selects more. The count says when to rebuild.

What a map knows

Coverage is keyed by definition, not by line. The map lists each source file's functions by signature header (the signature with its whitespace removed: g(x::Int), (s::S)(y)), in file order, and a testset's entry names the functions it executed by position in that list (functions = { "src/P.jl" = "1-3,9" }). A function counts as executed when any line from its signature to its end ran. Edits elsewhere in a file move line numbers but not headers, so a map stays valid while the code around it changes.

  • Methods sharing a name are told apart by their headers. If two definitions in one file have the same header (for instance under @static if), their coverage is joined.
  • A function that moves to another file is still found, when that header is defined in exactly one other file of the map.
  • A renamed or re-signed function has a new header, so the map lacks it. It is selected like a new function: by the testsets that executed another method of its name and the testsets that mention the name, and printed as UNCOVERED when neither exists.
  • Only a rebuild refreshes coverage for new, renamed and rewritten code.

Blind spots

  • Coverage comes from one run. A branch taken only on some seeds or thread schedules is missed by the testsets that did not take it that time.
  • Coverage counts lines, not specializations. A @generated body, or code run only at compile time, is covered when it is generated. Code inlined into a dependency's precompiled image is not covered at all.
  • From Julia 1.14, evaluating a definition counts its line as executed. A runner that includes the package's files, instead of loading the package with using, marks every function it defines as executed by every testset.
  • Names are matched as identifiers, with no scope. A local variable that shares a changed global's name selects too much. A name written as :TOL, var"TOL" or Symbol("TOL") counts as a mention; a name built at run time (Symbol(prefix, "TOL"), a loop over names(M)) selects too little.
  • Testsets are run by name. A testset with an interpolated name, or one inside a loop, cannot be mapped: build stops on the first and warns on the second.
  • Code outside the mapped source directories (scripts/, benchmarks/, registered dependencies) is not covered. A change there selects only the static-analysis testsets.
  • A static-analysis testset cannot say which files it reads, so any .jl change selects all of them, a test-only edit included (JET then runs for a test edit).
